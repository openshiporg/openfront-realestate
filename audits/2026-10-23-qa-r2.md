## Blocker

### QA-001 · dashboard · The QA admin still gets "Access Denied" on every dashboard route
- URL: https://openfront-real-estate-production.up.railway.app/dashboard/signin
- Steps: Sign in with the `realestate` credentials. Then open `/dashboard`, `/dashboard/platform/listings` or `/dashboard/platform/store-settings`.
- Expected: The dashboard home with its sidebar.
- Actual: Every route renders the Access Denied card. With the admin's own session cookie, `authenticatedItem` returns `{ name: "QA Admin", role: null, activeBrokerage: null, brokerageMemberships: [] }`. The user has **zero** `BrokerageMembership` rows. The round-1 fallback in `activeBrokerageIds` (`features/keystone/access.ts:53`) only covers users with exactly one live membership, so it cannot help here. The role even reads as `null`, because `Role` read access needs `isOperator`.
- Fix:
  - **Data/Euler:** give user `c2806bca129936b531c9327ae` an active owner/admin membership in the QA brokerage (and ideally set `activeBrokerage`), or create the admin through the app's own init or invite flow.
  - **Product:** a user whose role has `canAccessDashboard` but who has no membership should see an explanation, not "contact your administrator".
- Impact: The whole dashboard, onboarding, Store Settings and the lead → showing → deal workflow remain **unverified after two rounds**.

## Major

### QA-002 · storefront · "Forgot password" is still a dead end, and it reveals which emails have accounts
- URL: /password-reset
- Steps:
  1. Request a reset for `qa.nobody@example.test`, which has no account.
  2. Request a reset for `qa.r2.20261023@example.test`, a real customer.
- Expected: The same neutral confirmation for both, and an email with a link back to the storefront reset page.
- Actual:
  1. Unknown email: "If an account uses this email, a reset link is on its way."
  2. Real customer: "Password reset is unavailable. Contact the office."
- Why it matters:
  - A buyer who forgets their password still cannot get back in.
  - The difference in wording tells anyone whether an email has an account (account enumeration). Keystone only calls `sendToken` for existing users, and that call fails because production has no SMTP.
  - Even once SMTP is configured, the email link is `${SMTP_STORE_LINK}/dashboard/reset?token=…` (`features/keystone/lib/mail.ts:72`, where `basePath` is `/dashboard`). That sends storefront customers to the operator reset screen instead of `/password-reset?token=` (which does render: "Set a new password"). The email subject is also "Your password reset token!".
- Likely files: `features/storefront/lib/data/account.ts:89-95` (return the same neutral message whatever the outcome, and log the failure server-side), `features/keystone/lib/mail.ts` (pick the storefront path for customers, or pass `baseUrl` and path from the storefront request), and the production SMTP env (Euler).

- Actual:

- Likely files: `features/storefront/lib/brandMarkRoute.ts` (use a relative `Location: /brand-mark.svg`, or the existing `getBaseUrl`), and `app/layout.tsx:28`.
